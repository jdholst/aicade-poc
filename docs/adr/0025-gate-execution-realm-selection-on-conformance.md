# Gate execution-realm selection on conformance

Phase 9 will select its Mechanic Execution Realm technology only after a runnable candidate passes the Execution Realm Conformance Suite in Sparkline's real browser architecture. Any raw-engine or forbidden-authority access, representative escape, inability to terminate runaway code without freezing the editor, opaque-handle leak, cleanup failure, or loss of controlled deterministic execution is a hard rejection; source scanning alone is insufficient, while performance and implementation ergonomics only distinguish candidates that first pass every boundary gate.

## 2026-08-06 browser-session amendment

The public conformance contract is `mechanic_execution_realm_conformance/v2`. The runner accepts one opaque, single-run conformance session rather than independently supplied candidate and host values. `createMechanicExecutionRealmConformanceSession` supports candidate-neutral non-browser checks, but it cannot mint browser-admission evidence even when its candidate self-declares `environment: "browser"` or its host observes a genuine heartbeat.

Browser admission must use `createMechanicExecutionRealmBrowserConformanceSession` and `mechanic_execution_realm_browser_session/v1`. The trusted harness captures a candidate endpoint and the existing runtime iframe as distinct objects, generates the fixed private session, candidate-endpoint, and runtime identities, and sends each endpoint one ordered initialization message. Per-probe challenges omit those identities, so an acknowledgement or response must use the endpoint's initialized identity rather than merely echoing caller-supplied challenge fields. Each candidate request and heartbeat receives a fresh cryptographic nonce. Before returning a probe result, the candidate endpoint must send the execution acknowledgement for the exact execute request; a termination response cannot mint evidence without that prior acknowledgement. Only trusted `MessageEvent`s from the exact captured and still-current endpoint can mint the module-private, single-use evidence associated with that probe. The runner atomically consumes the session before the suite and disposes it afterward; explicit disposal is also available for abandoned sessions.

Ticket 08 must:

1. Keep the whole-game runtime iframe separate from the Mechanic Execution Realm candidate. A candidate endpoint may be a dedicated sandboxed iframe or a host-owned Worker, but the selected technology remains replaceable behind the endpoint protocol.
2. Load both endpoints before constructing the session, retain `sandbox="allow-scripts"` without `allow-same-origin` for candidate/runtime iframes, and let the trusted factory establish identity. Do not accept a caller-provided runtime or session ID as proof.
3. Implement the exported one-time initialization, candidate request/execution-acknowledgement/response, and runtime-heartbeat challenge/response protocol types. Install endpoint listeners before constructing the session, retain only the first initialized identity, send the acknowledgement immediately after the trusted endpoint dispatches an `execute` request, preserve the challenge's probe/action fields, and return the real probe result from the candidate endpoint. Never acknowledge `terminate` as execution evidence.
4. Pass the factory's opaque `session` directly to `runMechanicExecutionRealmConformanceSuite`. Do not pair a candidate adapter with an independently healthy iframe, translate evidence into booleans or structural receipts, or use `environment` metadata as admission evidence.
5. Require all unchanged 32 probes and ten hard gates to pass in the real browser path before comparing candidate performance or ergonomics.
